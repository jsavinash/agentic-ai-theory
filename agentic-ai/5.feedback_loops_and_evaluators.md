# Feedback Loops & Evaluators in Agentic AI: Architectural Design

This document explains the systems, scoring methodologies, and engineering patterns used to build continuous **Feedback Loops** and automated **Evaluators** for autonomous agent systems.

---

## 1. The Necessity of Runtime Evaluation

Traditional LLM apps rely on *pre-deployment* offline benchmarking against fixed datasets. **Agentic AI** systems generate open-ended, multi-step execution paths that cannot be fully predicted ahead of time — so quality must be enforced **at runtime**.

Runtime evaluation wraps the agent in a continuous feedback loop where every intermediate action, reasoning step, and tool output is graded before the state machine advances.

```text
 ┌──────────────┐      ┌──────────────┐      ┌───────────────┐
 │  Agent Node  │ ───> │  Evaluator   │ ───> │ Score Check   │
 │  (Generates) │      │   (Grades)   │      │ (Pass / Fail) │
 └──────────────┘      └──────────────┘      └───────────────┘
        ▲                                            │
        │             [ Fail: Loop Feedback ]        ▼
        └────────────────────────────────────────────┘
```

---

## 2. The 3 Types of Runtime Evaluators

A resilient ecosystem layers evaluator types by cost and trust level:

### A. Deterministic Evaluators (Code-Based)

The fastest, cheapest, most reliable line of defense — programmatic assertions, run in milliseconds.

- **Examples:** JSON Schema enforcement, regex filters, compiler/interpreter checks, database constraint checks, test suites against generated code.
- **Usage:** applied immediately after structured tool calls or code generation. In benchmark terms these are **execution-based evaluators** — the standard used by SWE-bench Verified (run the tests) and MCP-Universe (format / static / dynamic checkers).

### B. Model-Based Evaluators (LLM-as-a-Judge)

For unstructured or subjective criteria where exact-match assertions fail — tone, safety compliance, semantic alignment.

- **Mechanism:** a separate, tightly constrained LLM receives the output plus a **rubric** and returns a structured scorecard (binary or 1–5) with rationale.
- **Bias controls:** use a *different* base model from the agent (cross-model judging), randomize option order, and calibrate scores against a labeled human sample — judges exhibit documented self-preference and position bias.

### C. Human-in-the-Loop (HITL) Evaluators

Humans remain the high-trust mechanism for high-risk boundaries.

- The loop pauses and publishes state to a UI when a guardrail is hit (large financial transaction, push to production).
- The human approves, rejects, or supplies corrective text that is injected back into context as an explicit correction — often via protocol interrupt mechanisms (AG-UI interrupts, framework "resume" commands).

## 3. Designing a Resilient Feedback Loop

Unbounded self-correction burns budget and hangs runtimes, so every loop needs explicit exit conditions:

```text
[Incoming Task] ──> [Agent Node] ──> [Evaluator] ──> Passes rubric?
                                                        │
                                    ┌──── No ───────────┴── Yes ──> [Next Step / Done]
                                    ▼
                            Max retries exceeded?
                              │ No → loop feedback into Agent
                              └ Yes → [Escalate to Human]
```

### Anatomy of an Evaluation Trace

When an evaluator fails output, it must not just say "Incorrect." It returns a structured **Diagnostic Payload**:

1. **Exact failure:** `"DB constraint failed: column 'email' must be unique."`
2. **Preserved intent:** a restatement of what the step was trying to accomplish (from the Intent Anchor).
3. **Corrective guidance:** hints or parameters pointing toward the right logic path — *without* writing the fix for the agent, which would short-circuit learning and overfit the correction loop.

## 4. Key Metrics for Agent Evaluation

| Metric | Definition | Failure Signal |
| :--- | :--- | :--- |
| **Correction Depth** | Mean feedback iterations needed to pass per task. | High depth → weak prompts or tool docs. |
| **Token Loop Cost** | Spend attributable purely to self-correction phases. | Rising cost → degenerate loops. |
| **Drift Ratio** | Fraction of iterations measurably closer to goal. | < 0.5 → oscillation; halt and escalate. |
| **False Rejection Rate (FRR)** | Valid outputs rejected by the judge. | High FRR → rubric too rigid or judge misaligned. |
| **pass^k** | Probability a task succeeds in **all k** independent runs. | Good pass@1 but low pass^k → unreliable agent. |

```text
pass^k = mean over tasks of ( Π over runs i=1..k of success(task, i) )
```

**Why pass^k:** single-run scores hide flakiness. Sierra's **τ-bench / τ²-bench** popularized pass^k precisely because an agent that succeeds once in three tries is not production-ready, no matter how good its best run looks.

## 5. Benchmark Grounding (2025–2026 Standard)

| Benchmark | What it evaluates | Evaluator style |
| :--- | :--- | :--- |
| **τ-bench / τ²-bench** | Policy-following, multi-turn tool use; dual-control (user and agent share actions). | Simulated environment + **pass^k** reliability. |
| **Gaia2 / ARE** (Meta, 2025) | Async, noisy, read-and-write assistant tasks with injected tool failures. | Pass rate + latency-adjusted scoring (anti-brute-force). |
| **MCP-Universe** | Real MCP servers across 6 domains; unknown-tool and long-context challenges. | Format / static / dynamic execution-based evaluators. Top models scored ~29–44% success. |
| **SWE-bench Verified** | Real GitHub issues → patch → run unit tests. | Pure execution-based. |

**Takeaway:** the field converged on **execution-based grading + reliability metrics (pass^k)** over vibes-based single-shot scoring. Your runtime evaluators should mirror that standard.

---

## 6. Architectural Summary

Feedback loops turn fragile single-shot predictions into reliable, self-correcting automation. **Decouple grading from execution**, layer deterministic checks under calibrated LLM judges with humans at the top, enforce retry ceilings with structured diagnostic payloads, and track correction depth, drift, FRR, and pass^k — so agents fix their own errors before a production user ever sees them.
