# Memory Governance & Retention Policies in Agentic AI

This document establishes the architecture, compliance guardrails, and data-retention standards for long-term agentic memory: how data is acquired, categorized, isolated, and deleted.

---

## 1. The Core Memory Governance Challenge

Long-term memory turns agents from stateless tools into persistent, context-aware systems — but **Memory Governance cannot be achieved by simply configuring a vector database**.

Because agents autonomously extract and consolidate facts across sessions, memory becomes a decoupled, durable data source with three failure modes:

- **Context Poisoning:** hallucinated facts consolidate into long-term profiles, causing permanent downstream drift. **Memory poisoning** is explicitly listed in the *OWASP Top 10 for Agentic Applications* (2025) — an attacker who can write one poisoned memory can steer every future session.
- **Compliance Violation:** inadvertent PII persistence breaks Right-to-be-Forgotten law (GDPR Art. 17, CCPA/CPRA).
- **Privilege Escalation:** a multi-agent framework reads a restricted user's stored state and carries those facts into an unrestricted namespace.

---

## 2. Tiered Memory Storage & Lineage Architecture

Memory is isolated into functional layers with strict ownership tags — never dumped into one flat namespace:

```text
┌──────────────────────────────────────────────────────────────────────┐
│                        RUNTIME MEMORY ROUTER                         │
│   ┌─────────────────────┐  Read/Write Tags   ┌───────────────────┐   │
│   │   Episodic Layer    │ <────────────────> │  Access Controls  │   │
│   │ (Timestamped Logs)  │                    │ (RBAC Invariants) │   │
│   └─────────────────────┘                    └───────────────────┘   │
│              ▲                                         │             │
│              └─────────── Consolidation Loop ──────────┘             │
│                                  ▼                                   │
│                       ┌─────────────────────┐                        │
│                       │   Semantic Layer    │                        │
│                       │ (Structured Profile)│                        │
│                       └─────────────────────┘                        │
└──────────────────────────────────┬───────────────────────────────────┘
                                   ▼
                        ┌─────────────────────┐
                        │  Forgetting Engine  │
                        │ (TTL / Deletion)    │
                        └─────────────────────┘
```

- **Episodic memory (history):** time-indexed raw execution traces — volatile, short retention.
- **Semantic memory (profile):** consolidated facts and preferences — durable knowledge distilled *out* of episodic loops.
- **Procedural memory (skills):** verified tool recipes and runbooks — promoted from episodic success, gated by human review.
- **Lineage metadata (required on every stored object):**

```json
{
  "memory_id": "mem_9x82f1",
  "namespace": "tenant_alpha:user_1102",
  "source_session_id": "sess_01HRA2...",
  "extracted_at": "2026-10-18T15:39:00Z",
  "confidence": 0.94,
  "data_classification": "PII-Restricted"
}
```

## 3. The Write-Consolidation Feedback Loop

Memories pass an automated pipeline before becoming durable facts:

1. **Extraction:** a dedicated *Memory Manager* LLM mines candidate facts from the closed session's trace.
2. **De-duplication & conflict resolution:** the manager checks existing vectors; contradictions (user changed their endpoint) mark the old node **stale/superseded** instead of overwriting — preserving audit history.
3. **Validation & filtering:** entries containing credentials, unsanctioned code, or high-risk PII are dropped at the boundary and flagged. **Redact before embedding** — vectors can leak sensitive content through inversion attacks.

## 4. Retention Rules & Compliance Policies

| Memory Subtype | Default Retention | Storage Pattern | Purpose & Compliance Context |
| :--- | :--- | :--- | :--- |
| **Session checkpoints** | 24 hours | Redis / memory-map cache | Resumable active workflows. |
| **Episodic logs** | 30 days | PostgreSQL + `pgvector` | Drift diagnosis and loop forensics. |
| **Semantic profiles** | Until user revocation | Hybrid vector-graph / SQL | Durable preferences and entity relations. |
| **Procedural skills** | Reviewed quarterly | Git-backed tool library | Reusable capabilities; human-approved. |

### The Forgetting Engine (Dynamic Erasure)

- **Temporal TTL eviction:** daily batch drops or archives rows where `current_date > extracted_at + interval '30 days'`.
- **Deletion package (Right-to-be-Forgotten):** user-facing inspect / correct / delete tooling at launch; the purge spans every store — vectors, caches, graph nodes, and derived summaries:

```sql
DELETE FROM agent_semantic_memory
WHERE namespace = :user_namespace;
-- Forced re-embedding invalidation + cache purge follows immediately
```

---

## 5. Security & Access Control Boundaries

- **Isolation at the storage tier:** never a single global namespace. Enforce **Row-Level Security** so an agent queries only the executing user's namespace.
- **Cryptographic envelope encryption:** sensitive semantic memories encrypted with customer-managed keys (CMK) *before* embedding; key revocation renders blocks unreadable.
- **Write provenance:** only the Memory Manager service principal may write to semantic stores — runtime agents hold read-only credentials, closing the direct poisoning path.

---

## 6. Architectural Summary

Memory governance makes persistent agents stable and compliant. Isolate layers, stamp lineage on every object, consolidate through a validating write loop, redact before embedding, and run TTL + deletion engines as first-class pipelines — and scale memory without surrendering control to drift or regulation.
