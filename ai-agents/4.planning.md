# AI Planning Architectures

**Planning** is the cognitive and architectural framework that transforms a high-level human instruction into a structured, executable roadmap. While a standard Large Language Model (LLM) acts on immediate intuition by predicting the next token, a planning-capable AI agent acts on intention — evaluating downstream consequences, handling structural branching, and organizing actions chronologically.

Without robust planning mechanisms, an autonomous system cannot reliably manage a **goal chain**, maintain **long-term autonomy**, or cleanly track its **state persistence**. This document covers the planning loop, the algorithmic archetypes that power it, and the failure modes that break it — with Part 5 (*Task Scheduling and Prioritization*) handling what happens *after* a plan exists.

---

## 1. The Core Planning Loop

Most autonomous planning architectures implement an iterative control loop, classically modeled after the **OODA Loop** (Observe → Orient → Decide → Act):

```text
 ┌──────────────────────────────────────────────────────────────┐
 │                                                              │
 ▼                                                              │
 [ Observe ] ──▶ Parse environment data, user intents,          │
 │               and system boundaries                          │
 ▼                                                              │
 [ Orient  ] ──▶ Hydrate context from persisted state,          │
 │               memory stores, and retrieval                   │
 ▼                                                              │
 [ Decide  ] ──▶ Compute the plan: sequence of downstream       │
 │               operations + success criteria                  │
 ▼                                                              │
 [ Act     ] ──▶ Invoke tools, execute code, run atomic ────────┘
                 actions; feed results back into Observe
```

The loop closes: every **Act** produces observations that may invalidate the plan, forcing a new **Decide**. Planning is therefore never a one-shot preamble — it is a *control cycle* that continues until a termination condition is met (goal satisfied, budget exhausted, or human cancel).

## 2. The Planning Problem: Why LLMs Struggle

A crucial reality check before the archetypes: **autonomous LLM planning is empirically weak without scaffolding**. The PlanBench benchmark (NeurIPS 2023) evaluated LLMs on International Planning Competition-style domains (e.g., Blocksworld) and found the best model (GPT-4) achieved only **~12% average success** generating executable plans autonomously — often producing plausible-sounding but invalid plans.

Three defenses have emerged, and every production planner uses at least one:

| Defense | Mechanism | Used By |
| :--- | :--- | :--- |
| **Search over generations** | Sample/expand multiple candidate steps; evaluate and backtrack | Tree-of-Thoughts, LATS (§3A, §3F) |
| **External validation** | A sound planner or verifier checks/corrects LLM plans (**LLM-Modulo** setting — dramatically more reliable than autonomous planning) | LLM + PDDL planners, test suites as verifiers |
| **Closed-loop replanning** | Never trust the full plan: act, observe, re-decide | ReAct, Plan-and-Solve with replan triggers (§3B, §5) |

The practical lesson: treat raw LLM plans as **hypotheses, not commitments** — cheap to generate, mandatory to verify.

## 3. Advanced Planning Archetypes

AI engineers deploy several distinct algorithmic strategies to give models planning capability, ranging from prompt-driven linear reasoning to non-linear search over action spaces.

### A. Chain-of-Thought (CoT) & Tree-of-Thoughts (ToT)

*   **Chain-of-Thought:** Forces the LLM to output reasoning step-by-step before the final answer, decomposing complex logical or mathematical hurdles into linear milestones. **Low cost, zero configuration** — but strictly left-to-right with no backtracking.
*   **Tree-of-Thoughts:** Generalizes CoT into an interactive branching tree. The agent generates multiple candidate next thoughts, scores each with a heuristic evaluator, and searches via **Breadth-First Search (BFS)** or **Depth-First Search (DFS)** — looking ahead or backtracking when a path dead-ends.
*   **Evidence:** on the Game of 24 benchmark, GPT-4 with plain CoT solved only **4%** of tasks; ToT reached **74%** — a direct measurement of what search adds over single-path generation (Yao et al., NeurIPS 2023).

### B. ReAct (Reasoning + Acting)

*   **Mechanics:** Tightly couples explicit reasoning traces with discrete execution steps in a loop: **Thought → Action → Observation → Thought…** The agent computes the next step from live environment feedback, not from the original prompt alone.
*   **Value:** Prevents planning in a vacuum — the roadmap adapts to real-world results in real time (tool errors, unexpected page states, API responses).
*   **Watch for:** goal drift over long horizons; every observation re-enters the context, so token cost grows with tool-output size.

### C. Plan-and-Solve

*   **Mechanics:** The agent maps out a macro-level roadmap of sub-tasks *before* invoking any execution tools, then executes each sub-task per the plan. Designed explicitly to fix the *missing-step errors* of naive zero-shot reasoning.
*   **Value:** Isolates macro-architecting from micro-execution — predictable logs, human-auditable before execution, and less context drift. In evaluation across ten reasoning datasets, Plan-and-Solve consistently outperformed zero-shot CoT and matched 8-shot CoT on math reasoning (Wang et al., ACL 2023).
*   **Watch for:** highly vulnerable to early failure — if the environment diverges from the plan's assumptions, every downstream step inherits the error (see §5, replanning triggers).

### D. ReWOO (Reasoning WithOut Observation)

*   **Mechanics:** Decouples reasoning from tool execution into three modules: a **Planner** writes the full step sequence upfront with `%X%` placeholders for evidence, a **Worker** executes all tool calls to fill those placeholders, and a **Solver** produces the final answer by substituting the evidence. Reasoning never interleaves with observation.
*   **Value:** Dramatic efficiency — ReWOO achieved **5× token efficiency** with a **+4% accuracy gain on HotpotQA** vs. interleaved baselines, and it degrades gracefully under tool failure. Because the modules are separable, distilled reasoning can be offloaded to much smaller models (the authors offloaded GPT-3.5-class reasoning into a 7B model).
*   **Watch for:** the upfront plan cannot adapt mid-execution — best for stable, well-understood workflows rather than open-ended exploration.

### E. Reflexion (Verbal Reinforcement)

*   **Mechanics:** An **Actor** attempts the task, an **Evaluator** scores the outcome, and a **Self-Reflective Learner** writes verbal lessons into an episodic memory buffer that are injected into the next trial. Agents learn from trial-and-error *without any weight updates*.
*   **Evidence:** Reflexion reached **91% pass@1 on HumanEval**, surpassing GPT-4's 80% at the time — gains from reflection loops alone, not fine-tuning.
*   **Best for:** retry-able tasks with clear feedback signals (code with tests, games, verifiable environments).

### F. Search-Based Planning (LATS)

*   **Mechanics:** **Language Agent Tree Search** unifies the above — it runs Monte Carlo Tree Search over the space of agent actions, using the LLM itself as policy *and* value function, environment feedback for scoring, and Reflexion-style self-reflection to improve later branches. It decides dynamically whether to exploit a promising path or explore a new one.
*   **Evidence:** state-of-the-art **92.7% pass@1 on HumanEval with GPT-4**, and a **75.9 average score on WebShop** with GPT-3.5 — matching gradient-fine-tuned systems without any training.
*   **Cost:** search multiplies inference calls; reserve it for high-stakes steps, not every action.

### Hierarchical Decomposition: The Plan Ladder

Production systems rarely plan at one altitude. Plans nest exactly like the goal-chain ladder: **strategic** (the goal) → **tactical** (milestones) → **operational** (task steps) → **atomic** (tool calls). Upper levels use ReAct/Plan-and-Solve for flexibility; lower levels use deterministic scripts where possible. See *Long-Term Autonomy and Goal Chains* for the full hierarchy.

## 4. Comparative Matrix

| Planning Strategy | Optimal Use Case | Core Strengths | Technical Trade-offs |
| :--- | :--- | :--- | :--- |
| **Chain-of-Thought** | Deterministic logic, single-turn debugging, arithmetic | Lowest latency; zero configuration | Linear and brittle; cannot react to live tool errors |
| **Tree-of-Thoughts** | Combinatorial puzzles (Game of 24: 4%→74%), tricky refactors | Native backtracking; explores alternatives before committing | Massive token consumption; high wall-clock latency |
| **ReAct** | Dynamic web browsing, open-ended API exploration | Highly adaptive to live environment feedback | Goal drift over long horizons; context grows with observations |
| **Plan-and-Solve** | Repeatable enterprise workflows, ETL pipelines | Predictable, structured, auditable before execution | Fragile to early divergence; needs replan triggers |
| **ReWOO** | Stable workflows; cost-sensitive, tool-heavy pipelines | **5× token efficiency**; separable modules enable small-model offload | No mid-plan adaptation; depends on upfront plan quality |
| **Reflexion** | Tasks with verifiable feedback (code + tests, games) | Learns across trials with no fine-tuning (HumanEval 91%) | Needs a reliable evaluator; costs extra trials |
| **LATS (search)** | High-stakes, hard decisions where cost is secondary | Best-in-class results (HumanEval 92.7%, WebShop 75.9) | Multiplies inference cost; complex to instrument |

**Selection heuristic:** start with **ReAct** for open-ended work and **Plan-and-Solve** for repeatable pipelines; escalate to **ToT/LATS** only at pivotal decisions; add **Reflexion** wherever a checker exists; reach for **ReWOO** when tool outputs dominate your token bill.

## 5. Replanning: When to Throw the Plan Away

A plan is a prediction; execution is data. Replanning policy determines whether the system is resilient or fragile:

*   **Milestone miss:** a completed step fails its success criteria → re-plan the *remaining* suffix, not the whole roadmap.
*   **Environment drift:** a persisted assumption becomes false (API changed, dependency blocked) → patch the affected branch.
*   **Resource shock:** token/cost budget or deadline pressure changes materially → re-optimize ordering (see Part 5 for scheduling interplay).
*   **Hysteresis:** never replan on a single noisy signal. Require the deviation to exceed a threshold *and* persist — otherwise hyper-reactive engines discard valid plans repeatedly, a failure mode called **plan over-correction**.

---

## 6. Engineering Bottlenecks

*   **Horizon Decay (The Fog of War):** As a computed plan stretches further into the future, variance in predicting environmental outcomes compounds — small systematic errors at step 2 become broken assumptions by step 30. **Mitigations:** shorten plan horizons (re-plan at every milestone), keep checkpoints close together, and attach explicit success criteria to each step so drift is detectable early.
*   **The Infinite Loop Defect:** When a tool throws a recurring exception (expired auth token, rate limit), an unconstrained agent retries the identical failing action until budgets are exhausted. **Mitigations:** per-action retry caps, exponential backoff with jitter, circuit breakers that route repeated failures to a human or a different strategy (see Part 5, §6).
*   **Plan Over-Correction:** Minor deviations trigger wholesale roadmap reconstruction, burning more compute re-planning than executing. **Mitigations:** the hysteresis rule from §5 — replan incrementally, only past threshold.
*   **The Plan-Act Capability Gap:** Plans routinely reference capabilities the agent doesn't actually possess (missing tool, insufficient permission). **Mitigations:** validate every plan step against the agent's registered tool/schema manifest *before* execution begins — the planning equivalent of a type check.
