# Goal Decomposition & Task Planning in AI Systems

**Goal decomposition** (or task decomposition) is the process of breaking a complex, high-level objective down into smaller, structured, and manageable sub-tasks. It is a foundational concept in both human productivity and **Agentic AI architecture**, enabling autonomous systems to tackle long-horizon goals without losing context or failing catastrophically.

Within this series, decomposition is the bridge between *planning* and *scheduling*: Part 4 covers the **algorithms** agents use to think (ReAct, ToT, plan-and-solve); this document covers **how goals are cut into task structures**; Part 5 covers **when the resulting tasks run**; and *Long-Term Autonomy and Goal Chains* defines the strategic → tactical → operational ladder that decompositions nest inside.

---

## 1. The Goal Decomposition Pipeline

When given a complex prompt, an AI agent coordinates execution by moving through a multi-tiered pipeline:

1.  **Objective Parsing:** Translating unstructured natural language into a concrete end-goal with explicit success criteria.
2.  **Sub-Task Generation:** Breaking down the main goal *recursively* until tasks become **atomic** — resolvable by a single prompt, API call, or code execution.
3.  **Dependency Mapping:** Sequencing tasks into structured execution graphs (Directed Acyclic Graphs) to determine what can run in parallel and what requires sequential inputs.
4.  **Execution & Validation:** Running each atomic task and testing its output against programmatic or LLM-based validation rules, feeding failures back into step 2.

```text
      [ HIGH-LEVEL GOAL: Create Pricing Report ]
                           │
       ┌───────────────────┴───────────────────┐
       ▼                                       ▼
 [ Sub-Task 1: Identify ]               [ Sub-Task 2: Collect ]
 [ Top 5 Competitors    ]               [ Competitor Pricing  ]
       │                                       │
       └───────────────────┬───────────────────┘
                           ▼
                 [ Sub-Task 3: Analyze ]
                 [ Gaps & Distill Data ]
                           │
                           ▼
                 [ Sub-Task 4: Generate ]
                 [ Final Report File    ]
```

### 1.1 A Formal Framing

Treat a decomposition as a verifiable data structure, not prose:

```text
Goal G  ──decompose──▶  Task set T = { t₁ … tₙ }
Each task  tᵢ = (inputs, action, outputs, verifier vᵢ, budget bᵢ)
Dependency graph D = (T, E)      where (tⱼ → tₖ) ∈ E means tₖ needs tⱼ's outputs

A decomposition is VALID iff:
  (1) Coverage    — the union of sub-task outputs satisfies G's success criteria
  (2) Atomicity   — every leaf tᵢ is executable in one bounded step with a checkable vᵢ
  (3) Acyclicity  — D contains no cycles (otherwise execution deadlocks)
  (4) Closure     — every non-root task's inputs are produced by another task or declared external
```

### 1.2 What Makes a Task "Atomic"

| Criterion | Test | Fails When |
| :--- | :--- | :--- |
| **Single bounded execution** | One model call or tool invocation completes it | The step secretly needs its own multi-step reasoning |
| **Verifiable output** | A concrete predicate (schema check, test suite, threshold) accepts/rejects it | "Improve the report" — no pass/fail possible |
| **No internal parallelism** | The step doesn't hide independent sub-work | "Research competitors" — actually five separate investigations |
| **Fits a context slice** | Inputs + expected output fit comfortably in one window | Requires megabytes of raw logs to even attempt |
| **Explicit contract** | Inputs, outputs, and side effects declared up front | Output type or required files are ambiguous |

## 2. Why Decompose: The Research Evidence

Decomposition is not a cosmetic organizational choice — it measurably changes what models can do:

*   **Scale does not fix composition.** The *compositionality gap* research (Press et al., Findings of EMNLP 2023) showed GPT-3-family models can answer **every sub-problem correctly yet still fail to compose the overall answer** — and the gap does not close as models grow. Explicit decomposition and step-by-step elicitation are the documented remedies.
*   **Decomposition unlocks easy-to-hard generalization.** Least-to-Most prompting (ICLR 2023) decomposed complex problems into simpler subproblems solved in sequence: on the SCAN compositional benchmark it reached **≥99% accuracy on every split with only 14 exemplars, vs. 16% for standard chain-of-thought** with the same model.
*   **Decomposition is the highest-leverage step in agentic pipelines.** In production research systems, a planner agent's decomposition of the user goal into parallel sub-investigations is exactly what produced the **90.2% single-agent margin** reported by Anthropic (Part 1, §1A).
*   **But decomposition itself can fail.** PlanBench showed raw LLM outputs are unreliable as autonomous plans (~12% success — Part 4, §2); the same caution applies to generated task trees. Decomposition quality must be validated, not assumed (§6).

## 3. Decomposition Methodologies

### A. Classical Foundations (1959–1980s)

The algorithms underpinning modern agent decompositions predate LLMs by decades and remain the load-bearing theory:

| Method | Mechanism | Modern Residue |
| :--- | :--- | :--- |
| **Means-Ends Analysis** (GPS) | Choose actions that reduce the difference between current and goal state | ReAct's Thought→Action loop; tool selection heuristics |
| **Goal Stack Planning** (STRIPS) | Push sub-goals and actions onto a literal stack; pop as preconditions are satisfied | Task stacks in agent TODO tooling; stack-based resumption |
| **AND/OR Trees** | `AND` nodes require *all* children; `OR` nodes need *any one* (alternative failovers) | Fan-out/fan-in pipelines with fallback routes |
| **Hierarchical Task Network (HTN)** | Domain-authored *methods* recursively expand abstract tasks into ordered subtasks | Agent "plan ladder"; recursive task expansion in ADaPT |
| **Partial-Order Planning** | Commit only to ordering constraints that are truly required; leave the rest free | DAG schedulers that parallelize everything not explicitly dependent (Part 5, §2B) |

The timeless lesson: **decompose along preconditions, not vibes.** A dependency is an information requirement — if task B needs A's *output*, that's an edge; if they merely share a theme, it isn't.

### B. Prompt-Based Decomposition (2022–2023)

*   **Least-to-Most Prompting** — two phases: *simplify* (decompose into subproblems ordered easy → hard) then *solve* (answer progressively, each answer conditioned on previous ones). Its SCAN result (§2) is the canonical demonstration that decomposition — not model size — closes compositional gaps.
*   **Decomposed Prompting (DecomP)** — an *inter-task controller* routes subtasks to a **library of specialized prompting modules**, each optimized for one sub-operation (sub-goal extraction, structure extraction, enumeration) and recursively decomposable. Modular sub-prompts can be swapped for trained models or symbolic functions per slot — decomposition as an interface contract.
*   **Plan-and-Solve** — one-shot: emit the full sub-task plan first, then execute (Part 4, §3C).

### C. Agentic Decomposition in Production (2023–2026)

*   **Planner agents + worker fan-out:** an orchestrator decomposes the goal and dispatches subtasks to specialists — the dominant pattern in production (Part 1, §1A; Part 2, §2.2).
*   **Structured task schemas:** HuggingGPT's planner emits machine-readable tasks — `{"task": …, "id": …, "dep": [prerequisite ids], "args": {…}}` — where `dep` fields *gate execution*: a task launches only after all its dependencies finish. This minimal schema (task ID + dependency list + typed args) is the skeleton of every durable decomposition format.
*   **The TODO-tool pattern:** coding agents like Claude Code and LangChain's `deepagents` standardize decomposition as a persisted todo list (`write_todos`) the agent updates as it progresses — decomposition made *visible, checkpointable, and interruptible* (Part 3's persistence applies directly to the todo artifact).
*   **Neuro-symbolic hybrids:** TwoStep (2024) lets an LLM decompose a goal into subgoals while a **classical PDDL planner** guarantees the ground truth: faster than solving multi-agent PDDL directly, shorter execution than single-agent plans, **guaranteed execution success** — and LLM-generated subgoals matched human-expert subgoals.

### D. When to Decompose: Upfront vs. As-Needed

| Strategy | Mechanics | Evidence & Trade-off |
| :--- | :--- | :--- |
| **Upfront decomposition** | Fully expand the task tree before executing | Auditable and schedulable (enables Part 5's DAG/CPA); wastes effort if early results reshape the goal |
| **Progressive ("rolling-wave")** | Decompose one level; execute; re-decompose the remainder | Adapts to findings; partially ordered plan stays current (Part 4, §5) |
| **As-needed (recursive)** | Try the subtask as-is; decompose *only* when the executor fails | **ADaPT** (NAACL 2024): up to **+28.3% ALFWorld, +27% WebShop, +33% TextCraft** success over strong baselines — decomposition depth adapts to both task complexity *and* executor capability |

**Rule of thumb:** decompose upfront when the environment is stable and auditable; use as-needed recursion when task complexity and model capability are both uncertain — over-decomposing an easy task costs orchestration overhead for nothing.

### Methodology Matrix (Consolidated)

| Methodology | Description | Key Advantage | Watch Out |
| :--- | :--- | :--- | :--- |
| **AND/OR Trees** | Rigid branches: `AND` = required steps, `OR` = alternative failovers | Logical clarity and strict execution mapping | Brittle when environment changes mid-branch |
| **HTN / Goal Stack (classical)** | Recursive method application / literal goal-action stack | Sound, predictable, rules-bound execution | Domain authoring cost; weak in open-ended settings |
| **Prompt-based (Least-to-Most, DecomP)** | LLM decomposes via prompting; specialized modules per subtask | Zero training; proven compositional gains | No execution guarantees — needs validation (§6) |
| **Upfront agentic planning** | Planner agent emits full task DAG with schemas | Fully schedulable; parallelism visible early | Premature commitment if goal is still fuzzy |
| **As-Needed (ADaPT)** | Recursive decomposition only on executor failure | Adapts depth to complexity *and* model skill | Failure-driven latency; needs a capable planner |
| **Neuro-symbolic (TwoStep, LLM+Modulo)** | LLM decomposes; classical planner/verifier proves the result | Guaranteed execution success where modeled | PDDL modeling overhead; static domains |
| **Dynamic Replanning** | Continuously injects new sub-tasks as environment/output changes | Resilience to tool failures and surprises | Over-correction risk without hysteresis (Part 4, §5) |

## 4. Granularity: Choosing the Cut

Granularity is the highest-frequency design decision in decomposition. Each task should carry an explicit contract:

```yaml
task:
  id: "collect-competitor-pricing"        # unique, referenced by dependents
  goal: "Fetch current list prices for the 5 named competitors"
  inputs:
    - "competitors[] from identify-competitors"   # references producer outputs
  action: "Run price_scraper tool per competitor"
  expected_output:
    schema: "pricing_table_v1"            # typed, machine-checkable
  verifier: "schema(pricing_table_v1) AND rows == 5"
  budget: { max_tool_calls: 12, max_tokens: 20000 }
```

| Cut | Symptoms | Correction |
| :--- | :--- | :--- |
| **Too coarse** | Subtask fails or stalls for hundreds of turns; context window overflows inside one "step"; failures are unattributable | Split until each piece has a single checkable outcome |
| **Too fine** | Orchestrator overhead exceeds task work; interleaving/context-switch costs dominate; progress stalls in bookkeeping | Merge steps that always run together with the same inputs |
| **About right** | A failure names exactly one task; retries are cheap; a reviewer can grade each output in isolation | — |

**Heuristics:** (1) if a subtask needs its *own* planner, it isn't atomic; (2) if two subtasks share 90% of inputs and always run sequentially, one task is hiding inside; (3) prefer 5–12 top-level branches — deeper fan is usually premature structure (see §3D: let execution tell you where the real cuts are).

## 5. Dependency Mapping & Execution Ordering

Dependencies convert a task *set* into a task *plan*:

*   **Edge rule:** add `tⱼ → tₖ` only when tₖ consumes tⱼ's **output** (data dependency) or mutates a resource tⱼ holds (resource dependency). Everything else is parallel-safe.
*   **Topological sort** orders a DAG in **O(|V| + |E|)** — the scheduler's unit of work (Part 5, §2B).
*   **Fan-out / fan-in:** independent siblings (§2, Sub-Task 1 ∥ Sub-Task 2) execute concurrently across workers, then merge — the parallel pattern that makes decomposition pay for itself (Part 2, §2.6).
*   **Critical path:** the longest dependency chain sets the floor on completion time; its tasks get scheduling priority, slack-bound tasks defer (Part 5, §2C).
*   **AND/OR semantics:** `AND` groups require all children before the parent closes; `OR` groups represent failover alternatives — record them in the graph or the scheduler will parallelize an either/or branch and waste budget.

> **Anti-pattern:** fabricating edges from narrative order ("step 3 comes after step 2" because the list said so). Narrative order is not a dependency — every fabricated edge destroys a parallelism opportunity and inflates the critical path.

## 6. Validating a Decomposition

Never execute a generated task tree without a gate. Run the decomposition through five checks:

1.  **Coverage:** does the union of leaf outputs satisfy the original goal's success criteria? Enumerate every clause of the objective and map it to a producing task — unmapped clauses are silent scope drops.
2.  **Acyclicity:** run a cycle check (topological sort fails ⇒ deadlock). Cheap, automated, non-negotiable.
3.  **Verifier presence:** every leaf has an executable `vᵢ` (schema check, test run, threshold). Tasks without verifiers cannot report failure and will drift.
4.  **Capability check:** each task's declared tools/permissions exist in the agent's manifest *before* execution — the plan-act gap from Part 4, §6.
5.  **Dry-run / rehearsal:** where possible, simulate or partially execute the plan — the **LLM-Modulo** pattern (Part 4, §2): an LLM proposes, an external verifier (planner, schema checker, test suite) disposes. TwoStep-style classical validation upgrades "looks right" into *guaranteed* where domains are modelable.

**Acceptance heuristic:** if a reviewer cannot grade each task's output in isolation and explain why the sequence terminates, the decomposition is not yet executable — regardless of how clean the diagram looks.

## 7. Core Benefits & Failure Modes

### Benefits

*   **Prevents Context Drift:** Mitigates hallucination risks from single-prompt execution over long durations — each task runs against a bounded, relevant context slice instead of a bloated history.
*   **Granular Error Isolation:** A failed process faults *one node*: debug, retry, or replace it without re-running the plan (blast radius = the task, Part 2, §1).
*   **Parallel Execution Efficiency:** Independent sub-tasks fan out concurrently across workers — the mechanism behind production systems' **90.2% breadth-first gains** (Part 1, §1A).
*   **Auditable Progress & Pacing:** Every task is a checkpoint: progress, cost, and remaining work become measurable — the basis for Part 5's prioritization and critical-path control.

### Failure Modes

| Failure Mode | Mechanism | Mitigation |
| :--- | :--- | :--- |
| **Over-decomposition** | Orchestration overhead exceeds task value; interleaving thrash | §4 heuristics; as-needed recursion (ADaPT) instead of maximum depth |
| **Under-decomposition** | A "step" hides its own planning; context overflow inside one task | Atomicity tests (§1.2); split on first evidence of hidden sub-work |
| **Wrong cuts (missing edges)** | Tasks run without required inputs → failures cascade downstream | Dependency closure check (§1.1 rule 4); dry-run before execution |
| **Premature commitment** | Full tree built on a fuzzy goal; early findings invalidate half the plan | Progressive decomposition (§3D); replan triggers (Part 4, §5) |
| **Subtask-goal drift** | Each subtree optimizes locally while the union no longer serves the original goal | Coverage check (§6.1) re-run at every milestone |
| **Compounding errors** | A wrong assumption at task 2 corrupts tasks downstream by task 30 | Verifier per leaf; contract-narrow interfaces between stages (*Long-Term Autonomy and Goal Chains*) |
